良い質問です。整理すると、cpgoが扱う「混在」には2つの意味があり、それぞれ対応状況が違います。

## 1. ディレクトリツリー内でファイルとディレクトリが混在している場合 → 対応済み

これは通常の使い方そのもので、`scanTree`（scan.go）が`filepath.WalkDir`でツリー全体を走査し、ファイル・ディレクトリ・シンボリックリンクをすべて`Entry`として記録します。

`sync.go`の`runSync`は、走査結果を種類ごとに複数パスで処理する設計になっています。

- **Pass A**: まず全ディレクトリを`MkdirAll`で作成（ファイルの置き場所を先に用意するため）
- **Pass B1**: 通常ファイルをコピー、シンボリックリンクを再作成（ファイルは`-jobs`で並行）
- **Pass B2**: ハードリンクを再作成（プライマリのコピー完了後）
- **Pass C**: ディレクトリの属性（mtimeなど）を深い方から修正（子を作った後だとmtimeが変わってしまうため）

つまり「ディレクトリの中にファイルとサブディレクトリが混ざっている」というのは前提として普通に処理されます。

## 2. コマンド1回の`<src>`として、ファイルとディレクトリを両方同時に渡す場合 → 非対応（1つだけ）

`main.go`を見ると、

```go
if fs.NArg() != 2 {
    fs.Usage()
    return 2
}
```

引数は`<src> <dst>`の2つ限定で、`<src>`は1つだけです。その後

```go
switch {
case info.IsDir():
    err = runSync(src, dst, opts)
case info.Mode().IsRegular():
    err = runSyncSingleFile(src, dst, opts)
}
```

と、`src`がディレクトリかファイルかで処理を分岐しています。つまり「複数のsrcを一度に、しかもファイルとディレクトリを混ぜて」渡すことはできません。1回の実行につき、srcはディレクトリ1つ、またはファイル1つのどちらかです。

複数の異なる種類のものをまとめてコピーしたい場合は、cpgoを複数回呼ぶ必要があります（あるいはシェル側でループを書く）。

## 補足：ハードリンクの扱いも一種の「混在対応」

`scanTree`は同じ`(dev, ino)`を持つファイルを検出し、最初の出現だけを`TotalBytes`にカウントして実際にコピーし、2回目以降は`HardlinkOf`に記録して後で`os.Link`で再現します。これも「同じツリー内に通常ファイルとハードリンクが混在するケース」への対応と言えます。

もし「複数src対応」を追加したい場合、`main.go`の引数パースと`switch`部分を拡張すれば実装できますが、READMEやCLAUDE.mdの「シンプルさ重視」という方針を踏まえると、ループで複数回呼ぶ運用の方がこのツールには合っているかもしれません。

## 共通の前提: 末尾の`/`は無視される

main.goで最初に`filepath.Clean`がかかります。

```go
dst := filepath.Clean(fs.Arg(1))
```

`filepath.Clean`は末尾の`/`を除去するので、`/path/to/dst`と`/path/to/dst/`はcpgoにとって完全に同じ文字列になります。つまりrsyncのように「末尾の`/`の有無で意味が変わる」仕組みには**なっていません**。挙動を決めるのは、後述する「実際に存在するかどうか・ディレクトリかどうか」のチェックのみです。

## ディレクトリモード（`src`がディレクトリのとき）

`dst`は常に「ミラー先のルートディレクトリ」として扱われます。

```go
if !opts.DryRun {
    if err := os.MkdirAll(dst, 0o755); err != nil {
        return fmt.Errorf("mkdir %s: %w", dst, err)
    }
}
```

- **存在しない場合**: `MkdirAll`が作成します（親ディレクトリごと自動生成）。
- **既にディレクトリとして存在する場合**: そのまま使われ、中身がsrcとの差分でミラーされます。
- **既に「ファイル」として存在する場合**: `MkdirAll`は失敗します（同名の通常ファイルがある場所にディレクトリは作れないため）。この場合はエラーになり、`main.go`の`logger.Error(err)`経由でエラーメッセージが出て終了コード1になります。

## 単一ファイルモード（`src`がファイルのとき）

`single.go`の`runSyncSingleFile`が判定します。

```go
destPath := dst
if dstInfo, err := os.Stat(dst); err == nil && dstInfo.IsDir() {
    destPath = filepath.Join(dst, filepath.Base(src))
}
```

- **`dst`が既存のディレクトリの場合**: `cp src dir/`と同じ感覚で、`dst`の中に`src`の元のファイル名でコピーされます（例: `cpgo file.txt /existing/dir` → `/existing/dir/file.txt`）。
- **それ以外（存在しない、またはファイルとして存在する）の場合**: `dst`そのものが「コピー先ファイルのフルパス」として扱われます。既存ファイルなら上書き対象になります。
- **親ディレクトリが存在しない場合**: 続く`MkdirAll(filepath.Dir(destPath), 0o755)`で自動的に作成されます。

```go
if !opts.DryRun {
    if err := os.MkdirAll(filepath.Dir(destPath), 0o755); err != nil {
        return fmt.Errorf("creating destination directory: %w", err)
    }
}
```

## まとめ表

| モード | dstが未存在 | dstが既存ディレクトリ | dstが既存ファイル |
|---|---|---|---|
| ディレクトリ (`src`がdir) | 自動作成してミラー | そのままミラー先として使用 | エラー（MkdirAll失敗） |
| 単一ファイル (`src`がfile) | そのパスへコピー（親dirも自動作成） | `dst/<srcのbasename>`へコピー | 上書き |

一点注意なのは、ディレクトリモードで「dstが既存ファイル」の場合のエラーメッセージが、`MkdirAll`が返す生のOSエラー（`mkdir /path: not a directory`のようなもの）そのままになっている点です。README.mdの設計方針に「All errors are user-facing, so messages should be clear」（CLAUDE.md）とあるので、もし気になるようであれば、`runSync`の冒頭でこのケースを事前に検出して分かりやすいメッセージを出すよう改善する余地はあります。


## Rcloneの場合

rcloneは常にソース側パスの末尾に / があるかのように動作する（＝ディレクトリの中身をコピーする）
- ソースが /path/to/src で、その中に one.txt, two.txt がある場合
- 宛先 /path/to/dst が存在しなければ、rcloneがそのディレクトリを新規作成し
- dst/one.txt, dst/two.txt としてコピーされます（dst/src/one.txt のようにネストされることはありません）
